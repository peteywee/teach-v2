## Exact normative change

C21 3.0.0 retains the native/daily recovery default in MIG-9, MIG-10, MIG-AC-6 and OQ-MIG-1, with only this exception:

For the FIRST ADDITIVE SYNTHETIC installation into the previously absent teach_v2_demo schema of existing t34ch project acqafjkdkdmtpnsxiesw on PostgreSQL 17, a candidate-bound encrypted, transactionally consistent application recovery set MAY replace the native restore point and native/daily mechanism prerequisite for that installation alone. Every condition below MUST be independently evidenced. Unknown, omitted, stale, contradictory or unverified required coverage MUST block installation. This is not platform-native equivalence, full Supabase disaster recovery, an ongoing backup policy or permission for future customer production, later demo migrations, deletion, relocation or overwrite. All other C21 and C52 gates remain mandatory.

MIG-10 retains same-major isolated restore and maximum 30-day freshness, and additionally requires restoration of the exact post-freeze captured set used for this candidate, not an older sample of the same method. Changes to candidate, migration bytes, capture method/configuration, coverage or target invalidate the binding and require fresh capture/rehearsal. MIG-AC-6 blocks unless either the unchanged native default or every exact exception condition is satisfied. MIG-12's isolation controls and manual exact-candidate apply gates are unchanged; its statement that MIG-9/MIG-10 are unchanged is qualified only by this explicit exception. OQ-MIG-1 retains the native default outside this exact scope. OQ-MIG-4 may name this exact recovery-set identity instead of a native point solely inside the exception.

Operations 3.0.0 §5 recovery reference and §8 steps 2–3 reference these same bounded conditions. Step 4 MUST use the reviewed isolated-schema lineage and exact additive SQL, not the public-schema legacy runner. No production credentials enter CI. No general remote execution or approval engine is added.

## Required evidence and procedure

1. Freeze exact source commit, tree and ordered migration IDs/SHA-256s. Read authoritative project/PG-major/schema/journal/role inventory. Prove this is the first installation and namespace does not exist and creator/runtime role names have no unapproved collisions; already provisioned roles must exactly match separately approved provisioning. Any pre-existing demo namespace, prior applied lineage, unexpected grant or unresolved dependency blocks. Treat an uncertain prior apply as reconciliation, not a fresh installation.
2. Inventory every candidate-affectable application object/data item and its transitive dependencies before capture. Cover schema definitions, rows, types/views, constraints/indexes, functions/triggers, nonsecret roles/membership, ACL/default ACL/RLS, extensions, sequences (last_value AND is_called), journals and dependencies. Per item, identify inclusion or explicit exclusion with reason, dependency analysis and independent proof that excluded items cannot be affected. Exclusion is forbidden for required items. No auth password hashes, session/refresh tokens, role passwords, API keys, Vault material or platform/encryption roots enter this set. If a required dependency cannot be safely captured and restored without excluded secrets, STOP.
3. Capture schema and rows from one consistent snapshot after freeze. Record snapshot start/end and method/configuration. Detect catalog/role changes outside MVCC; use a separately approved no-concurrent-DDL plan. Sequences are not MVCC snapshot data: separately establish a reviewed consistent sequence-state capture and verification protocol; unresolved concurrent advancement blocks. Record required extension availability/version compatibility. Capture no storage object bytes unless candidate-affectable, separately approved and restore-verifiable; relevant uncaptured storage blocks. The existing scoped content archive is NOT a qualifying recovery set.
4. Before real capture, obtain approval for exact categories/omissions, source, encrypted destination/access, retention, separate key handling and isolated restore target. Encrypt before approved persistent storage; do not put plaintext dumps, keys, secret-derived hashes or sensitive row contents in chat, Git, CI or logs. Verify encrypted readback and successful authorized decryption. An encryption key is not bundled with its ciphertext. New access/credentials/key transmission require their own exact approval.
5. Actually restore that captured set to a disposable isolated PostgreSQL 17 target, with compatible extensions and explicit nonsecret role recreation/mapping verified against captured role definitions, membership and grants. Required roles and extensions must be deliberately recreated or independently verified on the isolated target; silent inheritance from the source cluster cannot satisfy this requirement. Disable restored external side effects/network integrations. Verify schema/catalog/rows via canonical checksums or equivalent full comparisons, ACL/default ACL/RLS, roles, sequence state and journal/dependencies. Record exact capture identity, target, database version, start/end, tool/method/configuration, commands/results and artifact hashes. A clean migration replay, Boolean claim, source review or JSON validator alone is NOT restore proof. Respect deletion-ledger/privacy requirements before any restored traffic; no restored service traffic is allowed in this rehearsal.
6. Rehearse exact candidate additive migration on the restored copy and compare preservation inventory before/after. It must not alter legacy/auth/storage/extensions/project configuration or global/inherited privileges. New creator defaults must be scoped and verified. Preserve legacy data, schema, constraints, functions, triggers, ACL/RLS, sequences and journals. Record denial probes and all discrepancies. Restore success without additive preservation proof is insufficient.
7. Only after independent review of actual evidence, request manual owner approval of exact candidate, migration IDs/hashes, target and recovery set. Immediately before apply recheck no drift/collision since capture. Apply transactionally with bounded locks/timeouts and abort on mismatch. Capture post-apply journal, schema reconciliation, legacy preservation and isolation readback. No automatic deployment or live apply is granted by this proposal or its validator.
8. Rollback stops v2 traffic/admission and preserves records, using transaction rollback or reviewed forward repair. NEVER restore the whole database over newer legacy writes, drop legacy objects or purge captured data as an automatic rollback. Failed/ambiguous apply requires readback before retry. The first-install exception is consumed once installation succeeds; subsequent work uses the default policy unless separately revised.
