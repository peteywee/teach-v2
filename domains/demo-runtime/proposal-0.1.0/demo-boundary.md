# Exact synthetic visitor boundary

All text here is proposed and inactive.

## Records and ownership

Organization owns DemoRun, Organization, Location, Membership, MembershipGrant and ReportingRelationship. Identity owns DemoPersona, Identity and ApplicationSession. A DemoRun has exactly one DEMO_ONLY Organization and one Location, exactly two DemoPersona bindings (LEARNER and MANAGER), two location Memberships, one learner bundle grant, one manager bundle grant and one demo_visitor grant on each Membership. Its single ReportingRelationship points from the manager Identity to the learner Identity at that same scope. No org_admin or observer grant exists.

DemoRun fields: id: DemoRunId; organizationId: OrganizationId; locationId: LocationId; status: ACTIVE|CLOSED|EXPIRED; createdAt: Timestamp; expiresAt: Timestamp (createdAt + 60 minutes, immutable); closedAt: Timestamp|null; closeReason: USER_EXIT|EXPIRED|null; admissionPrefix: reduced-resolution IPv4 /24 or IPv6 /56 network prefix, or SHARED_UNKNOWN. Final-state invariant: ACTIVE has null closedAt/reason; CLOSED has USER_EXIT; EXPIRED has EXPIRED; terminal timestamp is immutable and not earlier than creation. No end-state rewinds. These are fields, not permission to update other owners' tables.

DemoPersona fields: id: DemoPersonaId; identityId: IdentityId (unique); demoRunId: DemoRunId; kind: LEARNER|MANAGER; createdAt: Timestamp. The pair (demoRunId, kind) is unique and immutable. IdentityStatus remains the existing ACTIVE/INACTIVE/DELETED set, with no new DELETED ingress. Display aliases are fixed content: “Alex, demo learner” and “Jordan, demo manager”; they are not real profile data. No password, Credential, Invitation, SetupToken, reset token, OAuth link or real-person identifiers are issued. An ordinary Identity cannot be converted into a DemoPersona, nor can a DemoPersona become an ordinary/customer Identity.

DemoRun has no mutable current-persona field. Current identity is determined by the one ordinary ApplicationSession cookie. All active sessions for both personas are serialized through the run's owner locking-read interface. At most one usable session exists per run after admission/switch; issued session history remains immutable except normal lifecycle fields.

## Five new commands, no hidden general provisioning path

1. BeginDemoRun, owner Organization. Public trigger accepts an empty JSON object only, byte-exact allowed Origin and the bounded admission controls below. A registered deterministic admission principal allocates a fresh server-generated run/organization/location and creates only those Organization-owned facts. It invokes CreateDemoPersona twice; existing CreateMembership twice; frozen-template PublishContentPack; initial AssignContent; and existing CreateApplicationSession for the learner through their owning command boundaries. Fixed grants/reporting are created by the Organization owner within this one declared command. All effects, lifecycle/audit facts and initial assignment commit in one transaction. No cookie is set before commit. Any failure rolls everything back.
2. CreateDemoPersona, owner Identity, INTERNAL. Only BeginDemoRun's fresh-run transaction context can call it, once for each fixed persona slot. It creates the Identity and immutable DemoPersona binding, records required creation history/audit and creates no reusable Credential. Ordinary CreateIdentity and its primary-credential rule are unchanged.
3. SwitchDemoPersona, owner Identity. Requires a valid current demo session and explicit organization/location tuple matching its run. Body target is exactly LEARNER or MANAGER, never an IdentityId, run ID or role/capability list. If target is already current, return 409 CONFLICT with no mutation. Lock run and revalidate current session and live run; resolve fixed counterpart via owner interfaces; canonical-revoke every still-ACTIVE session for either persona; invoke CreateApplicationSession for the counterpart; append audit and commit atomically. Return new cookie only after commit. No retained credential or run deadline is renewed. A run may issue at most 100 ApplicationSessions total, including the initial session and revoked/expired historical sessions. Under the run lock, read the authoritative Identity-owned count before issuance; at the limit return 409 PRECONDITION_FAILED and retain the current session. Close/logout and expiry remain available and do not issue a session. This allows all ten practice cycles while bounding repeated-switch storage.
4. CloseDemoRun, owner Organization. Visitor call derives the run from its valid demo session, validates explicit tuple and requires the demo close capability. Named expiry-principal call is RECORD-scoped to exactly one run whose immutable deadline has passed; it does not require live-run availability, which would prevent safe expiry. Under the run lock, ACTIVE becomes CLOSED for user exit or EXPIRED for expiry; invoke RevokeDemoSessions in the same transaction; append exactly one terminal audit/history result. Failure rolls back. Repeated internal close of a terminal run returns its original terminal state/time without duplicate writes. A replayed revoked visitor cookie still returns 401; it is not a recovery credential.
5. RevokeDemoSessions, owner Identity, INTERNAL. Callable only by CloseDemoRun with an exact owner-validated run/organization context; resolves that run's two personas through owner interfaces and invokes the existing canonical ApplicationSession revocation implementation for their ACTIVE sessions. No direct foreign writes, credential changes, Identity deletion or alternate revocation writer.

The initial assignment is performed by the explicitly registered admission principal with the narrow internal fresh-run policy, not by pretending the manager is the caller. Publish and Assign commands still enforce content validity, ownership, membership, exact version and audit. Each command keeps one owner entry point; orchestration is not a second repository writer.

## Principal and capability registration

Two fixed non-human principals are proposed, both deterministic AutomationActors and neither a DevelopmentAgent:

- automation:demo-admission-v1: capability organization.demo.begin; scope DEMO_NEW_RUN. It can allocate only a fresh server-minted DEMO_ONLY scope and use only the declared internal command graph for that allocation. It cannot target, enumerate, read or mutate existing/customer organizations. No role bundle or PLATFORM scope exists.
- automation:demo-expiry-v1: capability organization.demo.close; scope RECORD, with exact record type DemoRun and only status ACTIVE with deadline reached, or terminal retry. It can enumerate only due synthetic run IDs through Organization's expiry query, then close each exact record. No content/learning/customer read or delete capability exists.

In-process dispatcher identity is resolved from an immutable, boot-validated principal manifest in the isolated backend, never from headers/body/environment strings supplied by a requester. This is a newly proposed explicit authentication method for these two local deterministic dispatchers; it does not provision external service credentials, OAuth grants, API keys or broad database permissions. Public or shared deployment remains separately gated. Missing principal registration/configuration disables demo admission/cleanup; a DevelopmentAgent has zero product capabilities.

New capability names: organization.demo.begin (BeginDemoRun), identity.demo.persona.create (CreateDemoPersona, INTERNAL/no grant), identity.demo.persona.switch (SwitchDemoPersona), organization.demo.close (CloseDemoRun), identity.demo.sessions.revoke (RevokeDemoSessions, INTERNAL/no grant). New demo_visitor bundle includes only identity.demo.persona.switch and organization.demo.close; both personas receive it on their exact location Membership. Existing learner/manager bundle definitions are otherwise unchanged.

## Current authorization and availability

All ordinary learner/manager operations run through their normal identity, membership, scope, capability, target, domain, transaction and audit checks. Add a synthetic-persona fence to every protected operation, including SELF reads/logout: resolve the unique DemoPersona and its run, require ACTIVE run and server time strictly before expiresAt, then require the operation in the fixed allowlist. Missing, contradictory or unreadable facts deny before protected work. An expired run yields the ordinary 401 unauthenticated body for all persona sessions even if cleanup cannot write.

For an Organization immutably classified DEMO_ONLY and bound one-to-one to DemoRun, authorization step 6 MUST read Organization's database-current DemoRun availability projection and permit only if the run is ACTIVE, server time precedes its immutable deadline, and operation is allowed below. This projection only removes capability effect; it never grants capability. No Entitlement instance is created. Non-demo organizations retain existing entitlement policy. Begin's pre-run allocation and the exact-record expiry close are the only explicit special evaluation paths; neither bypasses owning invariants or audit.

Common persona allowlist: ReadCurrentSession, ListOwnMemberships, RevokeApplicationSession, SwitchDemoPersona, CloseDemoRun.
Learner adds: ListOwnAssignments, ReadAssignedContentVersion, StartLearningSession, RecordProgressEvent, CompleteLearningSession, ReadOwnLearnerState.
Manager adds: ListTeam, ReadTeamMemberLearnerState, AssignContent.
Everything else denies, even if a normal manager bundle includes its capability or a future route is mounted. Synthetic personas cannot create memberships beyond their original scope, receive additional grants, invite/offboard users, link credentials, certify or gain customer access.

## Session, replay and concurrency

Use only __Host-teach_session with current C12 cookie attributes and verifier. Normal 12h absolute and 30min idle lifetimes are unchanged; 60min run lifetime is an additional access restriction. No session credential appears in JSON, browser storage, logs, audit, receipts, URLs or saved idempotency responses.

BeginDemoRun and SwitchDemoPersona issue new secrets and are NON-RETRYABLE. The browser must not automatically retry them. Concurrent anonymous Begin requests may allocate distinct runs; only the last delivered cookie is available to that browser, and inaccessible prior runs expire. Bounded rate/capacity controls count every committed run, so a lost response is not free/unbounded allocation. If a request succeeds but its response is lost, read current session to establish what the browser actually possesses; if no live session is available, explain that the visit could not be recovered and offer a deliberate fresh start. Do not reconstruct or replay a secret from an idempotency key.

All run-sensitive writes lock/revalidate the same run before their ordinary target/session locks, including assignment/start/progress/complete/switch/close. A write that linearizes before close/deadline can commit; after close, expiry or session switch it fails. Lock ordering is run → current session/personas → membership/assignment/learning session → receipt/audit, consistently across owners; PostgreSQL transaction/locking evidence must prove no stale authorization window. The run's database-current clock check occurs after acquiring locks, not from an old request timestamp. Current authority is revalidated within the mutation transaction. Read snapshots must not return protected content after a run-close check loses its serialization race.

## Reset, logout, expiry and retention

Reset is two deliberate steps: CloseDemoRun → after confirmed success clear all protected UI state → BeginDemoRun. They are not one atomic transaction. If Close outcome is unknown, read current session before proceeding; do not claim reset complete. If Close succeeds and Begin fails, show “Previous demo ended. A new demo could not be started.” and a fresh-start action. The old visit never becomes usable again. A repeated old Close returns 401 to the browser; double reset cannot reset a different visitor.

Sign out in the demo uses CloseDemoRun and expires the session cookie on confirmed success. Existing RevokeApplicationSession also remains valid and revokes the presented session; a run left without access is closed later by expiry. Both paths clear all user/run-specific memory and prevent back/refresh/shared-device disclosure. A stale-session 401 clears protected UI/cookie locally but is not reported as a server-side successful close.

The named expiry job scans at most 100 due runs per invocation, one transaction per exact run. It can be retried safely and emits no duplicate terminal history. Enforcement of expiry never depends on the job running. An interrupted job resumes from authoritative run state. Cleanup here means terminalizing access and revoking sessions, not deleting data. All synthetic facts, idempotency evidence, reduced-resolution network prefixes and history are retained in the isolated demo store; no purge/anonymization executor is admitted. Creation/deadline/terminal clocks are explicit; physical-disposition policy remains RETAIN_NO_AUTOMATED_DELETE. This makes no privacy-erasure promise and does not change one-year audit policy.

## Admission bounds and public-data handling

Exactly 10 admissions per normalized network prefix per rolling hour; 100 total admissions per rolling hour; 1,000 total retained DemoRun records per isolated store, including closed, expired and orphan runs. The lower of these limits controls. Counts/check+insert serialize transactionally on the admission gate. Client-provided proxy/IP headers are never trusted; use only deployment-verified peer information, otherwise SHARED_UNKNOWN (all such clients share one bucket). Store only /24 IPv4 or /56 IPv6 network prefixes, not full addresses. Prefixes remain potentially identifying data and are explicitly included in the demo record class; they are not called anonymous. No email, name, contact field, free-text learner response, file upload, analytics or third-party telemetry is admitted.

Capacity/rate rejection is 429 with the standard error envelope and Retry-After where computable; unknown capacity/dependency is 503, not success. There are zero run/persona/content/session writes on rejection. Reset does not release capacity. Raising limits, purging rows or enabling indefinite public operation needs separately reviewed authority. Limits may be lowered without expanding authority. Two-persona membership and response/assignment quotas (defined in learning-definition.md) and the 100-ApplicationSession lifetime cap bound storage per run as well as the run count.

A valid normal non-demo cookie blocks Begin with 409 PRECONDITION_FAILED and no changes: the user must explicitly sign out through the normal path first. A live demo cookie also blocks Begin with 409; offer Continue or explicit Reset. Malformed, revoked, expired or orphan demo cookies may be discarded for a deliberate Begin but never become authority or an upgrade. Anonymous GET never allocates state.
