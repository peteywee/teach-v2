## 1. Finite selected demo, not a customer-product decision

Each admitted synthetic DemoRun owns a distinct demo organization and a distinct synthetic copy of one published teaching pack. Content is organization-owned for this run only; nothing selects the future customer/global-catalog model, grants cross-tenant publication, admits customer uploads, or labels material customer-approved. The operator-controlled demo setup invokes the Content owner boundary. There is no general publisher UI or HTTP route.

The complete lesson has exactly three ordered required single-choice steps. Each step contains meaningful instruction, a scenario question, choices, an authored expected choice and explanatory feedback for every choice. A pure server engine records whether the chosen answer matches the authored answer. That boolean is per-response teaching feedback, not a numerical score, mastery formula, pass/fail assessment or certification. Session completion means all three responses were accepted and persisted, regardless of answer match. The learner may practice again through a new assignment, not edit history.

One run permits ten assignments total: one initially provisioned through AssignContent and nine deliberate manager-created assignments. Every assignment permits exactly one session and each session exactly three canonical response records: maximum ten sessions and thirty ProgressEvents. At the assignment cap a fresh command returns `409 PRECONDITION_FAILED` before any side effect. Matching-key retries still return the existing result. The parent package supplies the independently bounded DemoRun lifecycle, provisioner and total-run limit.

These are explicit selections bundled into package approval, not additional questions to ask the owner separately. Content format limits, canonical bytes, database indexes and cursor mechanics are engineering definitions. Content ownership, completion meaning, deliberate repeat semantics and per-response feedback are semantic choices and must be named in the package; none is inferred to authorize real-customer policy.

## 3. Content schema, ownership and publication

One canonical schema, exact `schemaVersion = "1.0.0"`, rejects additional fields. Its top level is `{schemaVersion, contentPackId, organizationId, version, title, blocks}`. `version` uses strict SemVer 2.0 including prerelease/build forms, not ranges or `latest`. `title` is 1–160 Unicode scalar values. `blocks` contains exactly three uniquely identified ordered ContentBlocks; all are required.

Each block is `{id, kind:"SINGLE_CHOICE", instruction, prompt, options, expectedOptionIndex, feedback}`. Instruction is 1–4000 characters, prompt 1–1000, 2–5 distinct option strings of 1–500 each, expected index is an integer in range, and one 1–2000-character feedback string exists per option. Text is plain text only. No scripts, HTML, remote media, legacy formats, free-form schemas or approval claims. Canonical payload size is at most 64 KiB.

Canonical bytes are deterministic UTF-8 JSON with sorted object keys, preserved array order, no insignificant whitespace, decimal integers, and unmodified valid strings. Duplicate JSON keys, floats, lone surrogates and unsupported properties reject. `ContentVersion` is the immutable pair `{version, digest}`, with digest `sha256:` followed by 64 lowercase hex characters over those payload bytes. Pack ID accompanies every ContentVersion reference. Organization ownership is included in the payload, so a copied pack for another run has a new ID, scope and digest. Exact full version equality includes build metadata even where SemVer precedence would compare equal.

ContentPack is one stable content identity with immutable version values, not a new ContentPackVersion entity. A parent Content-owned identity/organization record plus create-only version rows is acceptable. Blocks are embedded canonical payload entities; no separate block table is necessary. Published versions never update. PublishContentPack changes from vague “transitions to published” to validated immutable creation; there is no invented draft/retired lifecycle or persisted publication status. Same pack/version/digest is a no-effect existing result; same pack/version with another digest is a conflict. Publication uses an explicitly SERVER_DERIVED natural key, not an implicit retry fallback, and first success writes its required audit atomically.

Pure engine v1.0.0 takes the exact pack, block ID, selected option index and fixed seed 0. It validates membership and option range, computes `matchesExpectedChoice`, and returns the selected authored feedback. It has no database, HTTP, browser or framework dependency. The server persists its exact evaluation with the response. Re-running the exact engine version from canonical content and input must produce identical bytes. The learner content query omits expected answers and feedback; accepted response results reveal that step's teaching feedback. No score or accuracy aggregate is calculated or displayed.

## 4. Assignment, session, response and completion

Assignment stores canonical ID, learner IdentityId, non-null OrganizationId and LocationId, ContentPackId, exact ContentVersion, server assignedAt and the sole `ACTIVE` AssignmentStatus. All fields are immutable. Actor and request live in audit/lifecycle records, not duplicated mutable actor columns. Its one-state machine creates ACTIVE and has no transition. ACTIVE is availability, not learning completion; losing membership/grants denies access without changing history.

Same-key AssignContent replay means the same assignment. A new deliberate key means a new assignment, even when learner and content are identical. There is no unique learner/content constraint. The manager UI uses “Assign again” for that deliberate action and preserves its original key across repeated clicks, failed delivery and retry. Manager state lists both assignments separately. Initial fixture assignment must also invoke this command, not bypass it with raw inserted rows. Only the parent-defined automation:demo-admission-v1 principal invokes that initial assignment inside BeginDemoRun fresh-run orchestration; it is not manager impersonation. That caller supplies the explicit key to AssignContent, without changing CLIENT_SUPPLIED into an implicit server fallback. Ordinary subsequent assignments remain manager-authorized.

One assignment has zero or one LearningSession. This deliberately narrows the current `LearningSessionUsesAssignment` many-to-one cardinality; both its registry entry and P05 registration must be revised explicitly. It does not weaken P05 `REQUIRED_ONE_ASSIGNMENT`: every session still has exactly one non-null authorized assignment. A fresh independent StartLearningSession key after a session exists returns CONFLICT; resume is a query of that same session. Repractice requires another assignment.

Session adds server startedAt and completedAt to existing `{id, identityId, assignmentId, status}`. Assignment FK and learner agreement become real constraints. Scope and exact version derive from immutable Assignment, avoiding redundant session scope fields. Status stays `ACTIVE -> COMPLETED`, terminal with no pause/reopen/abandon state. CompletedAt is null exactly while ACTIVE.

ProgressEvent stores ID, session ID, exact pack ID/version/digest, event schema version 1.0.0, sequence 1–3, immutable server evaluation and server recordedAt. It is append-only, with no lifecycle/status field. Unique session/block and session/sequence keys prevent a second accepted response. The client supplies only block ID and selected option index; server-owned match/feedback/engine version cannot be asserted by the client. New responses must be for the next unrecorded block; invalid, out-of-order and duplicate new-key submissions fail without writes.

CompleteLearningSession locks the same session as append. It verifies three unique ordered persisted responses then atomically transitions once and appends required audit. It does not accept client counts, “success”, score or mastery. A race has exactly one serialization: an accepted append commits first and completion includes it, or completion commits first and a later new append fails. If responses are missing, completion fails PRECONDITION_FAILED and remains ACTIVE. Repeated completion is a conflict, not idempotent success. If a completion response is lost, the UI reads current state rather than inventing a second completion effect.

## 5. Retry, quota, transactions and audit

AssignContent, StartLearningSession and RecordProgressEvent keep already selected CLIENT_SUPPLIED keys. The parent `CommandReceipt` namespace is canonical authenticated actor reference/class + organization + location + operation + key. It binds the canonical validated payload, including exact targets and scope, but not the incidental request ID. Effect, receipt and required audit/lifecycle records commit atomically. Authorization is checked again before replay. A 24-hour replay horizon is additionally bounded by the live DemoRun and current authority. Retain receipts/key-digest tombstones; do not purge or silently reuse an expired key. No session credentials or bearer tokens belong in receipts.

A same-key, identical committed response may replay without a new ProgressEvent even after session completion; that is retrieval of an old result, not acceptance of a post-completion learner action. A new key still faces the ACTIVE gate. Changed payload with an old key returns the existing registered `IDEMPOTENCY_KEY_REUSED`, not a second effect.

Serialize run quota checks so two independent assignment commands cannot both pass when only one slot remains. Obtain any DemoRun locking/read service through its owning boundary; Learning cannot directly import another module's repository. Lock/serialization ordering also covers current-grant revocation versus protected commands. A wrapper transaction alone does not prove this ordering.

Assignment creation requires one success AuditEvent plus one LifecycleEvent whose initial snapshot reconstructs every authoritative assignment field. C23 AUD-7 replay must equal current state. Publish, session start and completion have their explicitly registered success audits. RecordProgressEvent is not security-sensitive by default and must not acquire a mandatory success audit by implication; its canonical response and receipt are atomic. Denials use existing C23 redacted/rate-bounded denial policy. Required-audit failure rolls back effects. Audit/lifecycle UPDATE or DELETE by application roles must fail.

Do not promote or emit `ContentAssigned`, `LearningSessionStarted`, `ProgressRecorded`, `LearningSessionCompleted` just because historical machine or C14 wording mentions them. They remain kernel candidates without explicit owning-contract event admission. Remove misleading candidate emission references from the revised machine/command/policy definitions. Audit actions and persisted ProgressEvent entities are not a business-event bus.

## 6. Exact read path and minimal UI data

Register the existing policy-named operations as owner application queries, not new mutation commands:

- `ListOwnAssignments`: Learning; C14 `/operations/25`, API `/routes/18`. Exact selected scope, current learner and own assignment predicate. Returns assignment records with exact content/title and existing session or null.
- `ReadAssignedContentVersion`: Content; `/operations/26`, `/routes/19`. Current active own assignment is resolved through a new `LearningAssignmentReadInterface`; returns public exact-version teaching content, never answers/feedback before response.
- `ReadOwnLearnerState`: Learning; `/operations/27`, `/routes/23`. Own identity only, selected scope, optional AssignmentId. Returns persisted per-assignment state and own recorded feedback.
- `ReadTeamMemberLearnerState`: Learning; `/operations/30`, `/routes/16`. Uses exactly current ListTeam visibility: manager direct reports intersected with organization/location, or already-authorized org_admin membership. Returns separate assignment completion/session facts and counts, not selected answers, answer-match flags or scores.

Parent supplies `ReadCurrentSession`, `ListOwnMemberships`, `ListTeam`. Manager needs no general content catalog: initial assignment is part of bounded synthetic provisioning, and “Assign again” uses the exact immutable content reference in an authorized existing assignment result. No new manager assigned-content read privilege is introduced.

Lists order by `(assignedAt, AssignmentId)` with default limit 20 and maximum 50; a validated cursor is only a continuation selector, never authority. Every query reapplies its current scope predicate. Empty in-scope data is empty; missing/out-of-scope targets are the same non-disclosing NOT_FOUND. Query failure never becomes a client-fabricated progress success.

LearnerState is a read-time projection, no table or mutation command. It is keyed by one Assignment and projection v1.0.0. Its opaque stable ID is `ls_` plus SHA-256 of the exact canonical tuple `["LearnerState","1.0.0",organizationId,locationId,identityId,assignmentId]`. Fields are exact identity/content refs, session or null, recorded/required block counts, next block and self-only recorded evaluations. A new version/assignment never inherits earlier completion. No percentage formula, totals called scores or cached second authority.
