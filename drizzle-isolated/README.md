# Isolated demo lineage: local preparation only

This directory is a separate, deterministic lineage targeting `teach_v2_demo`.
It is not a replacement for, an edit to, or permission to execute the historical
`drizzle/0000`–`0006` public-schema migrations on a shared database.

## Build and verify

- `pnpm exec node scripts/db/compile-isolated-schema.mjs` verifies source pins,
  the historical journal, exact generated bytes, manifest and isolated journal.
- `pnpm exec node scripts/db/compile-isolated-schema.mjs --write` regenerates
  these exact files offline. The compiler rejects unreviewed historical SQL,
  source changes and journal changes; extending this lineage requires review.
- `pnpm exec node --test scripts/tests/validate-isolated-schema-lineage.test.mjs`
  checks deterministic output, lexical qualification, drift rejection and the
  fail-closed local-target gate.
- `TEACH_ISOLATED_DB=1 DATABASE_URL=<disposable-loopback-test-url> pnpm exec node
  scripts/db/migrate-isolated-schema.mjs` applies only these verified bytes.
  The executable rejects remote targets, URL target overrides and non-test
  database names. No live database execution is implemented or authorized.
- `TEACH_DB_SCHEMA=teach_v2_demo TEACH_ISOLATED_DB=1
  DATABASE_URL=<disposable-loopback-test-url> pnpm exec node --import tsx
  scripts/db/run-isolated-schema-proof.ts` runs the PostgreSQL 17 proof including
  the actual application callback. The selected local connection must be able to
  create/drop disposable test databases and synthetic temporary roles.

The compiler recognizes identifiers separately from string literals and comments,
and recursively visits dollar-quoted SQL/PLpgSQL bodies. All application tables,
foreign keys, trigger functions, `%ROWTYPE` references and helper calls are
explicitly schema-qualified. Actual PostgreSQL builtin functions and the `C`
collation are qualified with `pg_catalog`. Index and trigger names are scoped by
their explicitly qualified owning tables, as PostgreSQL requires.

Two historical dynamic sections are replaced offline, not executed and then
repaired: the immutable-trigger loop becomes explicit statements, and the
public-wide security sweep becomes security statements limited to the newly
reserved namespace. There is no runtime SQL remapping and no `search_path`
routing requirement.

## Execution and ownership

The local runner uses one transaction and advisory lock, refuses adoption of a
pre-existing namespace without a verified journal, checks current-role ownership
and verifies the full applied hash/timestamp prefix. Its Drizzle-compatible
journal is `teach_v2_demo.__drizzle_migrations`. A rerun is a checked no-op.
Unrelated `public.__drizzle_migrations` and `drizzle.__drizzle_migrations` are not
read, modified or adopted. Historical migrations and snapshots remain immutable.

The lineage enables RLS on its 22 application tables and its journal, with no
browser policies or grants. It revokes schema, table, sequence and function
access from `PUBLIC`, and from `anon`/`authenticated` if those roles exist. It
does not create roles, grant runtime access, disable a project's Data API,
change API exposure settings, or mutate another namespace.

Schema-local default-privilege revokes cannot negate a creator's global default
`PUBLIC EXECUTE` on new functions. Therefore these statements alone are not
evidence of secure future-object defaults. The explicit function revokes and
denied schema `USAGE` protect the committed lineage. A dedicated creator's
global function-default policy, least-privilege runtime grants, effective
browser-role privileges and Data API non-exposure still require separately
approved configuration and live evidence. Every later function must also receive
explicit reviewed privileges. No global default policy for a legacy creator is
changed by this lineage.

## PostgreSQL 17 local proof

`scripts/db/verify-isolated-schema.mjs` creates two disposable local databases
and four uniquely named, temporary roles. It also creates local NOLOGIN `anon`
and `authenticated` placeholders if absent, and removes only the placeholders it
created. Existing local API role attributes are never changed. It records and compares representative
legacy namespace/object inventory, owners, ACLs, RLS/policies, default ACLs,
sequence state, rows and journals before and after migration and runtime work.
It verifies two equivalent clean replays, a no-op rerun, journal-tampering
rejection, refusal to adopt foreign-owned or unjournaled existing namespaces,
all FK/trigger namespace bindings and negative role probes.

The proof alone creates a dedicated synthetic creator and changes only that
new creator's global function default, then tests effective privileges on future
tables, sequences and functions. A separate synthetic non-owner, non-bypass
runtime role receives only the demo DML grants and explicit demo-only test RLS
policies needed to exercise the application. It cannot read/write the protected
legacy fixtures or migration journal, use either journal/legacy sequence, create
tables or invoke the protected legacy function. A synthetic browser role cannot
read/write/invoke any tested demo object. Both named API roles retain their
representative legacy public read/function access while being denied demo
table/write/function/sequence access. The application runs under a hostile
`search_path` containing shadow helpers, builtin functions and aggregates; ten
direct probes prove those hostile builtins really are resolvable unqualified.

`verifyIsolatedSchemaProof({ exerciseRuntime })` accepts the real application
exercise exported by `scripts/db/exercise-isolated-schema-runtime.ts`. Set
`TEACH_DB_SCHEMA=teach_v2_demo` before importing application code. The exercise
covers admission, recipe content, idempotent start, three responses, completion,
persona switch, manager read, close and required audit writes. All temporary
databases and roles are removed on completion.

These are controlled local proofs, not proof that an unknown shared project has
safe ambient privileges. `PUBLIC` grants, role memberships and ownership can
grant access across schemas; a schema name is not an independent security
boundary. The real runtime/browser roles and existing legacy grants must be
inventoried without altering legacy permissions before any shared deployment.
No local proof authorizes credentials, remote grants, remote migrations,
publication, deployment or spending.
