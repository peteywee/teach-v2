# Proposed hosted backend successor: local preparation only

This is not approval, admission, deployment readiness, or a working hosted demo. Historical H01/H02 source and metadata remain unchanged. H02 remains the sole provider entrypoint and denies every request. The successor composition also denies unconditionally; no environment flag, injected factory, matching JSON or source digest grants authority. This change creates no roles, credentials, grants, schedules, provider settings or database objects.

## Bounded architecture

Reuse only the existing t34ch project, isolated `teach_v2_demo` lineage and existing fifteen API operations/seven assets. Do not wipe legacy objects, create a third project, incur charges or introduce customer-production infrastructure. The exact provider IDs still require readback and owner-bound candidate review, not inferred names.

The source-closure inspector inventories recursively reachable relative imports from backend, binding, pool, transport and disabled composition roots, plus explicit runtime file reads, all seven assets, route definitions and lockfile. It permits only pg/drizzle-orm package roots. Its hashes prove source integrity only, not approval. The local successor builder compiles this closure, retains pg/drizzle-orm and recursively installed runtime dependencies, and inventories every output byte. It produces a disabled local bundle, NOT provider approval. Two clean-source builds and packaged fifteen-operation/seven-asset tests establish bounded local reproducibility. A separate clean install with pnpm12.8.1, frozen unchanged lockfile and ignored lifecycle scripts succeeded with 36 packages reused from the content-addressable store and 0 downloads. The builder verifies installed application-lock equality, actual TypeScript 7.0.2 and both compiler configurations. Bundled package versions and every byte are recorded. Provider installation and independent tarball-integrity attestation remain distinct from this local evidence. An eventual provider builder must also prove that neither secrets nor DB clients reach browser assets. No generated source manifest is accepted as self-authenticating authority.

The new transaction runner retains existing owning application/repository semantics but sets transaction-local statement (5s), lock (2s), idle-in-transaction (5s), and PostgreSQL 17 transaction (10s) deadlines before application work. It uses unnamed parameterized statements through existing Drizzle behavior; no prepared name, session SET or startup migration is introduced. Provider compatibility, rollback, timeout failure and pooled-session reuse must be established with actual Supavisor and PG17 readback before activation. Local success cannot establish provider compatibility.

The inert pg options builder fixes transaction-pool port 6543, verified CA TLS (including hostname validation through pg/Node), max two connections, 3s connect and 10s client query deadlines. It accepts discrete server-side fields, never a connection URL that can override SSL options. The retained-pool seam creates once on first use and closes once. No live factory is supplied or invoked. The role proposal is a dedicated nonowner runtime with no superuser/BYPASSRLS/DDL/journal/legacy access, separately from the migration creator. RLS policies and minimal grants must be locally proven and independently reviewed, then separately authorized on the exact target; using a project-owner credential is not a fallback.

The finite disabled binding captures source commit/tree, built-artifact and closure hashes, schema, lineage/model-proof hashes, actual Node24 patch, pnpm12.8.1, exact project/deployment/origin, runtime role and credential revision. All are necessary integrity selectors and none is authentication. Operational approval is Patrick’s explicit approval through the agent/tool deployment workflow, not a runtime authorizer, digest, JSON document or environment flag. The separately selected accepting artifact consumes only server configuration; it cannot select itself through an HTTP request.

## Expiry execution design

Retain the unmounted always-forbidden expiry endpoint. Existing application authentication rejects expired runs regardless of scheduling; physical cleanup is not guaranteed by that check. A future scheduler must have its own explicit bounded identity, credential revision, approved invocation frequency and target binding. It may invoke only a no-body POST with no scope/actor supplied by a request, use existing bounded batches of at most 100, lock/recheck each run and preserve transactional revocation/audit semantics. Replayed/concurrent invocations must be idempotent. Unknown authentication or stale evidence denies before constructing dependencies. No live scheduler, public endpoint or shared bearer secret is created in this preparation.

## CI loopback topology correction

The historical 48-stage lane retains its original Docker service. A published-port Docker bridge is not equivalent to the isolated migration guard’s server-reported loopback requirement: the URL can say 127.0.0.1 while PostgreSQL sees a bridged interface. The failed first PR CI attempt was rejected by that guard; no permission or host allowlist was relaxed.

Only the Node24 lane starts a second disposable container from the already-cached official postgres:17.11-alpine image, with pulling disabled, host networking and an explicit 127.0.0.1-only listener on55432. No host mounts, public port publication, firewall changes or privileged flags are used; data and socket directories are temporary memory filesystems. A unique run/attempt/random identity, server address, port, database, cluster name and PostgreSQL17 readback must match before the fixture connection is exported. The fixed image and read-only root are checked. Another listener or container causes refusal, never termination or reuse.

Each Docker operation is bounded; startup polling is bounded; the whole workflow step has a25-second timeout. Failed or uncertain creation is reconciled by ownership-checked inspection and cleanup, not retried. An unconditional cleanup step runs before lifecycle recording, verifies exact ownership and removal, and fails if cleanup cannot be proven. The temporary runner itself is discarded by GitHub after the job. Tests cover failure/timeout/foreign-resource cases through a Docker-operation fixture and actual occupied local sockets. Actual Docker startup and cleanup are established by the subsequent CI run, not by those simulated cases. Existing loopback migration restrictions and provider activation gates remain unchanged.
